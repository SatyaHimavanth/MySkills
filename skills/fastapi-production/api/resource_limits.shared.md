# API Resource Limits — Shared

## Purpose

Prevent individual requests from consuming unbounded CPU, memory, database work, bandwidth, storage, or paid downstream resources.

OWASP API4 identifies unrestricted resource consumption as a widespread API risk.

## Required limits

Review each endpoint for request body size, list/page size, batch size, upload size, nested object count, string length, query complexity, request timeout, downstream timeout, concurrent work, and expensive-operation frequency.

## Pydantic/FastAPI bounds

```python
page_size: int = Query(default=25, ge=1, le=100)
name: str = Field(min_length=1, max_length=120)
items: list[ItemRequest] = Field(max_length=100)
```

Do not rely on frontend validation as a security/resource boundary.

## Expensive endpoints

Examples:

```text
large search
report generation
document parsing
AI inference
bulk export
```

Use stricter rate limits, timeouts, payload bounds, concurrency limits, and asynchronous jobs where appropriate.

## Fan-out

Estimate downstream work generated by one request.

```text
1 API request
  → 100 downstream calls
```

A burst of 100 API requests could become 10,000 downstream calls. Bound fan-out explicitly.

## Timeout hierarchy

Use a deliberate hierarchy such as:

```text
client/proxy timeout
    > API request timeout
    > dependency timeout
```

Every timeout must be finite.

## Batch limits

Batch endpoints need explicit maximum counts and should avoid quadratic processing.

## Database resource protection

Bound pagination, search depth, export size, expensive joins, and query complexity. Large exports should usually become durable jobs.

## Forbidden

- unbounded `limit`
- unbounded uploads
- unbounded batch processing
- unlimited downstream fan-out
- relying only on rate limiting while payload size is unrestricted
